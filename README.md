# MCPサーバー／クライアントの設計・実装レビューガイド

Model Context Protocol（MCP）の設計・実装時に確認したい観点を、人間が読むだけでなく、AIコーディングツールにもそのまま渡せるMarkdownのガイドにまとめたものです。

> **Status: Public Beta（v0.9.1-beta）**
>
> - 前提とするMCP仕様: [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)（現行版は [latest](https://modelcontextprotocol.io/specification/latest) で確認してください）
> - 最終レビュー: 2026-10-02
> - 検証は読み取り専用のWeb検索MCP 1件に限られます。未検証の範囲は [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md) にまとめています。
> - 実装レビューの検証には [v0.9.0-beta](../../releases/tag/v0.9.0-beta) を使いました。v0.9.1-beta では構造化エラーの例（§4.4）を仕様に合わせて修正しましたが、修正後の版での実装検証はまだ行っていません。

## なぜこのガイドを作ったのか

MCPサーバーは、SDKやAIコーディングツールの整備によって作り始めやすくなりました。一方、実際に作ってみると、仕様やSDKを読んだだけでは決められないことが次々に出てきます。ツールの粒度、Descriptionの書き方、入力検証、出力件数とペイロードの上限、成功条件、エラーで返す情報、サーバーとクライアント／ホストの責務境界などです。

これらは多くのMCP実装で繰り返し出てくる論点なので、判断のための設計観点を一度整理しました。実際にコードを書くのはAIコーディングツールなので、人間もAIも同じものを読める形にしています。

自分で実装したWeb検索MCPにこのガイドを適用したところ、次のような問題が見つかりました。

- 上流がHTTP 200を返し、SDKの例外も起きていないのに、検索そのものは実行されていなかった
- 自己診断用のツールを検索ツールと同じ一覧に置いたら、モデルが通常の調査でも呼び、検索が二重に実行された
- サーバー側でタイムアウトを長めにしても、ホスト側の既定値（約60秒）で打ち切られうる状態だった
- `retryable: false` を返したら、引数を直せば通る場合でもモデルが処理を止めた

どれも、プロトコルに準拠しているかどうかでは判定できない問題です。

## ガイドの特徴

- 人間が設計判断の確認に使え、AIコーディングツールへもそのままコンテキストとして渡せる
- MCPサーバーだけでなく、クライアント／ホストとの責務境界も扱う
- 設計前、実装時、テスト、実装後レビューのどの段階でも参照できる
- チェックリストだけでなく、判断の理由、ツール仕様の記述例、AIへの指示例を含む
- MCP仕様に基づく記述と、筆者の推奨・実験結果をラベルで区別している

### 記述のラベル

ラベルがないと、AIは仕様上の必須事項と筆者の判断を同じ重要度の指示として扱ってしまいます。そのため、本文の記述には次のラベルを付けています。

| ラベル | 意味 |
|---|---|
| `[MCP Specification]` | MCP仕様（2026-07-28版）で定義されている事項 |
| `[Recommendation]` | 本ガイドの推奨設計。仕様上の要件ではない |
| `[Interoperability]` | ホスト／SDK実装との互換性のための注意 |
| `[Security]` | セキュリティ上の注意 |
| `[Experiment]` | 筆者の限定的な実装検証で観測された事実。条件はガイドの Appendix B |

`[Experiment]` は、1実装・1ホスト・1モデルでの観測です。発生率や一般則としては読まないでください。

## 使い方

### AIに渡すもの

```text
対象MCPの要件 ＋ 現在の設計または実装コード ＋ このガイド
                        ↓
     実装の修正点 / 採用しない項目と理由 / ガイドへの指摘
```

要件として、最低限次を伝えてください。

- MCPの目的と利用者
- Read／Writeの別と副作用
- 扱うデータ区分
- 接続する外部サービス
- 利用するクライアント／ホスト
- コスト、レイテンシ、網羅性などの優先順位

最後の優先順位は、実装者（AIを含む）に推測させてはいけないものです。優先方針が変わると、Descriptionの書き方、既定値と上限、ツール構成まで連鎖して変わります。

### 依頼例

実装のレビューと、ガイド自体のレビューは2回に分けて依頼します。

1回目（実装のレビュー）:

```text
このMCPの設計と実装を、添付のレビューガイドに基づいて確認してください。

最初に、目的、利用者、副作用、データ区分、利用するクライアント／ホストなど、
レビューに必要な前提が不足していれば質問してください。

結果は次の2つに分けて報告してください。

1. 実装へ反映すべき問題
2. 今回は採用しなくてよい項目と、その理由

各指摘では、根拠にしたガイドの節、想定される失敗、推奨する修正、
確認方法を示してください。

MCP仕様上の要件、ガイド独自の推奨、相互運用性上の注意、
限定的な実験結果を混同しないでください。
```

2回目（ガイド自体のレビュー）:

```text
今回の実装レビューを踏まえて、レビューに使ったガイド自体の矛盾、不足、
過剰な要求を指摘してください。

各指摘では、該当するガイドの節、想定される失敗、推奨する修正を示してください。
```

2回目を省くと、ガイドが更新されなくなります。ガイドへの指摘は、[Issue](../../issues) で共有していただけると次の版に反映できます。

### 全項目を実装する必要はありません

副作用の有無、利用者数、データ区分、監査要件に応じて採否を判断してください。たとえば読み取り専用・個人利用のMCPに、承認フローやEnterprise相当のテレメトリは過剰です。採用しなかった項目は、理由と一緒に残しておくと次のレビューの判断材料になります。

### AIのレビュー結果で人間が確認すること

- ガイドの項目を機械的に全適用していないか
- 採用／不採用の理由が、対象MCPのリスクと規模に合っているか
- 仕様上の要件とガイドの推奨を混同していないか
- コードを読むだけでなく、実際に使うホスト上での評価計画まで提案しているか
- ガイド自体への指摘が妥当か

このガイドは、AIにレビューを任せきりにするためのものではありません。人間とAIが同じレビュー基準を共有し、指摘の根拠をガイドの節番号で追えるようにするためのものです。

## 既存のMCP開発Skillとの関係

Anthropicの公式プラグイン [`mcp-server-dev`](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/mcp-server-dev/README.md) は、ユースケースの問診、デプロイ方式とツール設計パターンの選択、scaffoldを支援します。本ガイドが主眼にしているのはその後の設計・実装レビューなので、競合ではなく補完関係にあります。

## 今後の予定

公式Skillで書き込み・更新系のMCPを作り、冪等性、承認、競合更新、実行後の状態確認を本ガイドでレビューする予定です。検証結果はガイドの Appendix B と変更履歴（ガイド末尾）に追加します。未検証の範囲が埋まった時点で 1.0.0 とします。
